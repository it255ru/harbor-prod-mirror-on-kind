# Backlog: Harbor active-active на KinD — прод-зеркало (форк)

**Статус (2026-09-25): P0–P6 выполнены (стенд собран с нуля, `make verify` 38 PASS / 0 FAIL, тесты отказов h41–h48 и h62 пройдены, документация переписана); план форка закрыт. Открытые вопросы — в конце раздела «Риски и заметки» и в P5 («Что осталось непроверенным»).**

Форк `harbor-active-active-on-kind` @ `7279079` (сам — форк `harbor-on-kind` @ `b65df71`); полная история, включая подробный backlog родителя (Phase 0–6, пункты H0.1–H6.2), — в git: `git show 7279079:backlog.md`. Здесь — только то, что относится к этому репозиторию.

**Цель:** как можно точнее воспроизвести конкретный боевой стенд: Harbor `2.14.3`, HAProxy + Keepalived на входе, Redis Sentinel, Patroni + Consul, S3 для блобов (Ceph в проде, Garage здесь) — на 14-нодовом KinD-кластере на одной машине. Назначение стенда: Docker- и Helm-репозитории для ВМ клиентов; Harbor проксирует внешние репозитории (proxy-cache проекты) и хранит локальные.

## Решения

Решения пользователя и решения автора плана помечены; последние открыты к пересмотру.

**Этого форка (2026-09-25):**

- **D11 — HAProxy + Keepalived заменяют Infra LB.** MetalLB и ingress-nginx убираются целиком; Keepalived держит плавающий VIP (VRRP) на `lb`-нодах, HAProxy за ним балансирует HTTPS-трафик на Harbor. Решение пользователя.
- **D12 — Harbor `2.14.3` / chart `1.18.3`, официальный образ Docker Hub.** Прод показывает версию `v2.14.3-fa517e2a`; считалось, что это вендорская сборка, недоступная из этой сессии, и по решению пользователя взят публичный `v2.14.3`. **Уточнено в P5 (2026-09-25): на собранном стенде `GET /api/v2.0/systeminfo` возвращает `harbor_version: v2.14.3-fa517e2a` — то есть `fa517e2a` это git-коммит, который официальный Harbor `v2.14.3` сам добавляет к номеру версии, а не отдельная сборка. Расхождения с продом по образу Harbor нет.**
- **D13 — внешний PostgreSQL понижен до `15.19-alpine3.24`** (у родителя — `18.6-alpine3.24`). Chart `1.18.3` документирует встроенный PostgreSQL `15.12`; решение пользователя — не полагаться на неподтверждённую совместимость с PG 18, взять последний патч той же мажорной ветки 15.x (стиль пина — как у родителя: alpine3.24). Тянет пересборку образа `hack/ha/patroni` (Phase P4).
- **D14 — образ Keepalived: собственная минимальная сборка (Alpine + `apk add keepalived`), не сторонний образ.** Решение автора плана (не пользователя) — открыто к пересмотру. Причина: тот же урок, что и с MinIO у родителя (D4a) — сторонние образы `keepalived` на Docker Hub не от вендора инфраструктуры, могут исчезнуть или перестать обновляться; собственная сборка по образцу `hack/ha/patroni` контролируема и закрепляется по digest базового слоя.
- **D15 — Harbor отдаётся через собственный nginx чарта (`expose.type: clusterIP`), не через Ingress.** Решение автора плана (не пользователя, следствие D11) — открыто к пересмотру. Без ingress-controller у чарта остаются `clusterIP`/`nodePort`/`loadBalancer`; `clusterIP` даёт Service `harbor` и 2 пода nginx-photon на `app`-нодах, которые сами маршрутизируют на core/portal/registry. Infra LB (HAProxy) работает в TCP-режиме (passthrough TLS) на эти поды, сертификат и CA — тот же Secret `harbor-ha-ingress-tls`, поэтому `getcert` и доверие ноды не меняются. Побочные эффекты: в `images.txt` появился `goharbor/nginx-photon`; `preStop` (post-renderer) добавляется и nginx; распределение core/portal за Service (kube-proxy) по логам больше не видно — V12 считает по подам nginx и registry.
- **D16 — Infra LB: один DaemonSet `infra-lb` (hostNetwork, Keepalived + HAProxy) на `lb`-нодах, отдельно от `harbor-lb`.** Решение автора плана (реализационное, по P2). Отдельно — чтобы сбой Infra LB не затрагивал PG/Redis. VRRP multicast на `eth0`, `virtual_router_id 51`, обе ноды `BACKUP` + `nopreempt` (адрес не «прыгает» обратно при возврате ноды), приоритет 100; Keepalived отпускает VIP, если локальный HAProxy `/healthz` (127.0.0.1:8405) не отвечает. Бэкенды HAProxy — поды nginx Harbor по отдельности (headless Service `harbor-nginx-headless`, `server-template`, проверка `GET /api/v2.0/ping` по TLS). Цель `make infra-lb` сохранена (новая реализация), файла `keepalived.yaml` из плана нет — всё в `hack/ha/infra-lb.yaml`. Demo-приложение (раньше `LoadBalancer` `172.20.0.101` от MetalLB) — `NodePort` 30500 на control-plane.
- **D17 — внутренние Service Harbor с `trafficDistribution: PreferSameNode`** (core, portal, registry, jobservice; проставляет `hack/helm-postrender.py`). Решение автора плана — открыто к пересмотру. Причина: у D15 был недостаток — nginx и core ходят к соседям через ClusterIP, и kube-proxy до NotReady (≈ 50 с) раздаёт новые соединения и на мёртвый под, из-за чего при потере `app`-ноды часть запросов висела до 30 с. На каждой `app`-ноде по одной реплике каждого компонента, поэтому вызывающий под предпочитает endpoint своей ноды; это только предпочтение — без локального endpoint kube-proxy откатывается на другие (при сбое одного пода поведение прежнее). Альтернативы отвергнуты: ускорять `node-monitor-grace-period` (ложные NotReady на общем диске, ради которых и подняты тайминги leader-election), `internalTrafficPolicy: Local` (жёстко: при падении локального пода трафик теряется), retry в nginx (не покрывает core → registry, где dial-таймаут зашит в Go-клиент core). Дополнительно проверки HAProxy Infra LB ускорены (`inter 1s fall 2`, `timeout connect 2s`). Поле есть в Kubernetes 1.34 (kind `v1.34.0`), на других версиях кластера нужна проверка.

**Унаследованы от родителя (в силе):**

- **D1 — 14 нод:** 1 control-plane + 13 воркеров, роль — label и taint `harbor-ha/role=<role>`: `app`×2, `lb`×2, `pg`×2, `redis`×3, `consul`×3, `s3`×1. Имена нод kind: `harbor-worker` (app), `-worker2` (app), `3–4` (lb), `5–6` (pg), `7–9` (redis), `10–12` (consul), `13` (s3). *Предположение:* S3 — одна нода.
- **D2 — Patroni + Consul** (подтверждено): PostgreSQL ×2, состояние в Consul ×3 (без ACL/TLS — лаборатория).
- **D3 — Redis: Sentinel (1 master + 2 replica).** Боевой режим неизвестен (на схеме «Redis Cluster», а chart принимает только `redis` и `redis+sentinel`); для форка принято, что Sentinel соответствует проду.
- **D4/D4a — блобы registry в S3 (Ceph RGW в проде); в лаборатории Garage `v2.4.1`** вместо MinIO: образы MinIO пропали с quay.io между двумя сборками родителя. Бакет `registry-blobs`, ключ `harbor`, Secret `s3-credentials`.
- **D5 — один лабораторный кластер за раз:** `CLUSTER=harbor`, `LB_IP=172.20.0.100` общие у трёх репозиториев (`harbor-on-kind`, родитель, форк).
- **D6 — критерий успеха в два этапа:** сначала работа стенда в распределении по 14 нодам (веха 1), только после неё засчитываются проверки отказоустойчивости (веха 2).
- **D7 — Harbor LB = HAProxy ×2** на `lb`-нодах перед PostgreSQL и Redis (адрес `harbor-lb.harbor-deps`, не вход в Harbor). PG: health-check Patroni REST `GET /primary`; Redis: `role:master` + подключённая реплика. Вход в Harbor — Infra LB (D11, D16).
- **D8 — минимальный объём:** Harbor app ×2, Harbor LB ×2, PostgreSQL ×2 + Consul, Redis ×3, S3, Infra LB. **Бэкапы PG/Redis и Prometheus с прод-диаграммы не входят.**
- **D9 — цвета green/yellow на схеме** для лаборатории не важны, сегментации сети нет. **D10 — Nexus не входит.**

## Целевая архитектура

```text
клиент -> 172.20.0.100 (Keepalived VIP, lb-нода) -> HAProxy (Infra LB, TCP passthrough) -> nginx Harbor (app) -> core / portal / registry -> HAProxy (Harbor LB) -> PostgreSQL primary / Redis master
                                                                                                          \-> Garage (S3, блобы)                     PostgreSQL state -> Consul
```

| Поток | Откуда → куда | Заметка |
|---|---|---|
| Вход | клиенты и администраторы → **Infra LB** (Keepalived + HAProxy) → Harbor nginx | TLS завершает nginx Harbor, сертификат — Secret `harbor-ha-ingress-tls` |
| Данные приложения | Harbor app → **Harbor LB** → PostgreSQL / Redis | Harbor LB стоит *перед БД*, не перед Harbor |
| Блобы registry | Harbor app → S3 | `disableredirect: true` |
| Состояние PG | PostgreSQL → Consul | DCS Patroni |
| Интернет | Harbor app → внешние registry | proxy-cache проекты |

## Критерии успеха (D6)

**Веха 1 — «стенд работает в распределении по 14 нодам».** Принимается, когда выполнено всё:

1. 14 нод `Ready`; роли по label/taint: `app`×2, `lb`×2, `pg`×2, `redis`×3, `consul`×3, `s3`×1.
2. Каждый компонент на ноде своей роли; реплики одной роли на разных нодах (кроме demo-приложения на control-plane).
3. Кластерные сервисы здоровы: Consul — 3 сервера и лидер; Patroni — 1 leader + 1 replica (streaming); Redis — 1 master + 2 replica и кворум Sentinel; Harbor LB ×2 и Infra LB ×2 (оба контейнера) `Ready`; VIP ровно на одной `lb`-ноде; nginx, core, portal, registry, jobservice — по 2 реплики на двух `app`-нодах; бакет S3 доступен.
4. Сквозной путь: UI через VIP отвечает 200; push/pull образа и OCI-чарта проходят; `make deploy-app` проходит; блобы в S3, а не в томе registry.
5. Нагрузка распределяется: запросы через VIP обслуживаются обеими репликами nginx и registry; HAProxy отдаёт трафик на текущий primary PG. (Распределение core/portal за Service по логам не видно — D15.)

**Веха 2 — отказоустойчивость** (`hack/tests/`, раздел 4 ранбука): засчитывается только после вехи 1. Обязательно перемерить: `h47 redis` (проверка нового способа задать пробы core/jobservice), `h47 pg` (PostgreSQL 15), `h47 lb` (Keepalived вместо MetalLB — цифры родителя неприменимы), `h44` (потеря `app`-ноды: теперь и nginx).

## Что унаследовано и подтверждено на родителе (Harbor 2.15.2, PostgreSQL 18, MetalLB)

Реализация и проверки родителя (Phase 0–6, H0.1–H6.2) переносятся в форк как код. **Результаты измерений родителя к форку неприменимы, пока P5 их не перемерит**: стек другой (Harbor 2.14.3, PG 15, Keepalived вместо MetalLB, nginx вместо ingress-nginx).

Что в коде и остаётся верным (справочник):

- **Размещение:** `topologySpreadConstraints` (`maxSkew 1`, `matchLabelKeys: [pod-template-hash]`) вместо обязательного `podAntiAffinity` (тот блокирует rolling update на двух нодах); `harbor-lb` — `maxSurge: 0`. Каждый воркер под таинтом роли: любой новый под нуждается в `nodeSelector` и toleration.
- **Harbor:** `jobLoggers: [database]` (не `file`: нужен RWX); Secret'ы `harbor-ha-secrets`, `harbor-ha-s3`, `harbor-ha-token`, `harbor-ha-ingress-tls` создаёт установщик один раз, никогда не пересоздаёт; ключ токена — PKCS#1 (`genrsa -traditional`); CA стабильный (`certSource: secret`), иначе после `helm upgrade` новые pull на ноде падают с `x509`; `preStop: sleep 15` (post-renderer), иначе rolling update даёт 502; `database.maxIdleConns 20` / `maxOpenConns 50` при `max_connections 200`; chart читает `existingSecret` через `lookup` — `helm template` без кластера даёт пустые пароли, проверять `DRY_RUN=1 make harbor-ha`.
- **Redis:** после потери ноды рестартовавший `redis-0` не должен становиться вторым master (расщепление мозга, потеря подтверждённых `INCR`): `start-valkey.sh` ждёт пиры при рестарте, Valkey с `min-replicas-to-write 1 / min-replicas-max-lag 10`, проверка HAProxy требует `role:master[^a-z]{1,4}connected_slaves:[1-9]` (в регулярках HAProxy `.` не захватывает перевод строки). Sentinel `down-after` 15000 (при `5000` общий диск вызывал ложные failover).
- **Общий диск хоста:** гигабайты записи (сборка образов с `dd`, большие push) стопорят etcd/apiserver, роняют controller-manager/scheduler (leader-election 60/40/10 с в `kind-cluster.yaml`), провоцируют failover Sentinel. Тестовые данные держать малыми.
- **Consul:** `-retry-join` только на *другие* серверы (иначе при быстром старте три пода образуют три отдельных кластера); имя пода — из `metadata.name` (Kubernetes не подставляет `$(HOSTNAME)` в `args`).
- **Garage:** образ без shell — `hack/ha/s3-init.sh` работает через `kubectl exec ... /garage`; liveness на порту S3 3900.
- **Кэш образов:** `docker save` образа, полученного по digest, теряет имя — образы сохраняются под `cache.local/...:cached` и переименовываются на ноде через `ctr images tag`; `make images-load` кладёт образ только в ноды своей роли; для роли `host` (образ node kind, базы сборок) Docker не хранит digest — тег без digest. `images-check`: `MISSING` — реестр ответил «нет/запрещено», `UNKNOWN` — таймаут/сеть (ничего не говорит об образе).
- **Proxy-cache:** кэшируются манифест платформы и блобы по digest, не тег и не индекс — при недоступном апстриме pull по тегу не работает; кэш появляется через ~20–40 с; поле URL для endpoint `docker-hub` игнорируется; удаление проекта через API не чистит S3 (для тестов — уникальные имена).
- **Тестовые данные Harbor:** удалять по **digest**, не по тегу (удаление артефакта убирает все его теги; так однажды пропал `python/hello:1.0`). Удаление артефакта не освобождает блобы S3 — только GC registry.
- **Patroni `synchronous_mode` (H6.2):** по умолчанию выключен; включается `patronictl edit-config -s synchronous_mode=true` (`on` даёт гарантию, пока есть sync-реплика; `strict` блокирует запись при потере реплики). Окно записи при потере лидера 16–33 с определяется `ttl 30 / loop_wait 10`. Решение — за пользователем (D8); скрипт `hack/tests/h62-sync-mode.sh`.
- **Окна отказов родителя** (ориентир, не результат форка): Kubernetes признаёт потерю ноды за ≈ 45–55 с; Redis master — ≈ 21 с без Redis; PG primary — ≈ 33 с без записи, ≈ 16 с 5xx; Consul — ≈ 3 с сбой записи PG; `app`-нода — задержки до ≈ 50 с, вытеснение подов через 300 с (`tolerationSeconds`).

## Риски и заметки

- 14 нод-контейнеров на одной машине: полный стенд ≈ 4,5–6 ГиБ RAM и ≈ 8 ГБ образов (+ кэш `~/.cache/harbor-ha`); «HA» здесь учебная — общий диск, ядро, никакой реальной изоляции отказов.
- Образы третьих сторон могут исчезнуть (MinIO): перед `make cluster-delete` рабочего стенда — `make images-save` и `make images-check`. Docker Hub на этом хосте медленный и нестабилен (первый `images-save` родителя — 57 минут).
- Непинованные зависимости ломают сборку со временем (случай Flask/Werkzeug): у Patroni-образа зависимости PyPI зафиксированы `constraints.txt`; пакет `keepalived=2.3.4-r2` Alpine может исчезнуть из индекса при обновлении ветки 3.24 — тогда пересобрать образ с новым пином и записать его здесь.
- Прод использует вендорскую сборку Harbor `v2.14.3-fa517e2a`; здесь — публичный `v2.14.3` (D12). Расхождение между ними не исследовалось.
